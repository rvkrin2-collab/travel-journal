# Редакционный процесс журнала

Это каноническая подробная спецификация для каждой законченной визуальной истории путешествия (`chapter`). Главой может быть день, часть дня, место, маршрут, событие, тема, несколько дней или всё короткое путешествие.

## Имена и совместимость

Канонический путь данных:

```text
data/<trip>/<chapter>-photos.json
data/<trip>/<chapter>-analysis.json
data/<trip>/<chapter>-ai-review.json
data/<trip>/<chapter>-author-review.json
data/<trip>/<chapter>-final-review.json
data/<trip>/<chapter>-storyboard.json
```

`chapter` — безопасный произвольный slug. Существующие `dayNN-*` являются совместимыми значениями `chapter`, но новый код не должен преобразовывать произвольный slug в `dayNN` и не должен требовать наличия номера.

## 1. Инвентаризация фотографий

Для новых материалов единственным источником загрузки является Google Photos Picker с постоянным хранением в R2. Cloudinary поддерживается только как read-only наследие уже опубликованных путешествий и не входит в новый workflow.

1. Получить точный список выбранных материалов из Google Photos Picker, уже скопированных в R2.
2. Записать `<chapter>-photos.json` с устойчивым идентификатором, URL, размерами и источником каждого кадра.
3. Проверить уникальность идентификаторов, доступность URL и соответствие количества источнику.
4. Зафиксировать fingerprint набора, чтобы старые analysis/review не применялись к изменившемуся списку.

## 2. Полный визуальный анализ

1. Открыть каждый файл как изображение с достаточной детализацией.
2. Сначала описать только наблюдаемое: объекты, сцена, люди, свет, техническое качество и неопределённости.
3. Не выводить содержание из имени, `public_id`, EXIF-времени, порядка или ожидаемого маршрута.
4. Контекст автора и маршрут использовать только после наблюдения и только как ограничение для осторожной атрибуции.
5. Сохранить запись для каждого исходного идентификатора в `<chapter>-analysis.json`.
6. Блокировать следующие этапы, если множества идентификаторов photos и analysis не совпадают один к одному.

## 3. Группировка и предварительный отбор

После анализа **всех** кадров:

1. Сгруппировать фотографии по реально наблюдаемым местам и событиям.
2. Найти визуальные дубли по одному объекту и функции кадра; общий фон сам по себе не делает кадры дублями.
3. Восстановить фактическую последовательность только при достаточных доказательствах; неопределённость сохранить явно.
4. Создать `<chapter>-ai-review.json` с решением для каждого исходного кадра.
5. ИИ предлагает одно главное фото, основную серию, «За кадром» и исключения, но не утверждает их.
6. Текст главы на этом этапе запрещён; допустимы только наблюдения и редакторские пояснения к выбору.

## 4. Первое утверждение: редактор фотографий

Редактор открывается как `editor.html?trip=<trip>&chapter=<chapter>`. Для совместимости он может принимать `day`, но внутри должен работать с `chapter`.

Редактор обязан:

- загрузить точный `<chapter>-photos.json` и соответствующий `<chapter>-ai-review.json`;
- показать весь исходный набор без фильтрации;
- сообщить количество photos, analysis и AI items и блокировать экспорт при несовпадении;
- показать источник и fingerprint предзаполнения;
- для каждого кадра дать ровно один статус: `hero`, `story`, `backstage`, `skip`;
- дать поля «Что на фотографии» и «Что важно рассказать»;
- сохранять и импортировать решения без потери неизвестных/невыбранных кадров;
- требовать ровно один hero и решение для каждого кадра перед экспортом.

Результат — `<chapter>-author-review.json`. Это первое обязательное утверждение автора. До появления и валидации этого файла запрещено создавать storyboard, финальный текст или страницу публикации.

## 5. Storyboard и текст

После первого утверждения:

1. Проверить author-review против точного photos fingerprint.
2. Использовать выбранные автором статусы без изменения.
3. Построить последовательность: начало → развитие → ключевой момент → финальная сцена, только если она подтверждается материалом.
4. Писать короткий текст только из изображений, полей автора, его заметок, подтверждённого маршрута и проверенных фактов.
5. Не придумывать события, эмоции, разговоры, обстоятельства или географию.
6. Сохранить storyboard; optional final-review может улучшать формулировки, но не менять отбор автора.

## 6. Preview и второе утверждение

Preview обязан:

- использовать storyboard, созданный из текущего author-review;
- показывать точный источник данных и предупреждать о любом fallback;
- никогда не подменять отсутствующий author-review более старым AI/legacy review как будто это утверждённая версия;
- проверять идентификаторы, fingerprint и отсутствие пропавших кадров;
- показывать главную серию, «За кадром», навигацию и требующие проверки факты;
- быть проверен на телефоне и широком экране.

Автор получает preview для второго прямого утверждения. Замечания сами по себе не являются разрешением на публикацию. После утверждения preview каждой главы страница статуса должна явно показать, что главы готовы, но путешествие ещё не опубликовано.

## 7. Публикация

Публикация разрешена только после прямой команды автора об утверждении preview. Автоматизация не должна:

- публиковать AI review или неподтверждённый preview;
- добавлять черновик в основную навигацию;
- менять обложку путешествия на hero новой главы;
- перезаписывать уже опубликованные страницы при обработке новой заявки.

Обложка путешествия — отдельное редакционное решение и меняется только по прямой команде автора.

Прямой командой считается отдельное действие автора в финальном блоке страницы статуса: автор выбирает главу для обложки, подтверждает публикацию всего путешествия и нажимает кнопку публикации. Команда допустима только при валидном подписанном авторском сеансе и после второго утверждения всех глав. Генератор обязан повторно проверить fingerprints, точное соответствие наборов и approvals каждой главы; интерфейс не должен считать утверждение последнего preview автоматической командой публикации.
